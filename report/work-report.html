2. The demo shop: what each skill did

backend-expert-v1 → server, database, design doc

  • One request renders the shop front (user + products + cart); cart changes return the new cart, so nothing is refetched. Idle pages send 0 requests.
  • Checkout is safe against double clicks: idempotency key, atomic stock update, cart consumed in one transaction, payment call outside any transaction.
  • Passwords: Argon2id at the OWASP minimum. Sessions: random token, only its SHA-256 stored. Order lookups check the owner inside the SQL and return 404 for other people's orders.
  • Rate limits per request type (login failures per account, checkout 10/min, reads 300/min), CSRF origin check, strict security headers, errors without stack traces.
  • Wrote BACKEND.md with assumptions, call map, capacity estimate and a Test Handoff (12 endpoints, authorization matrix, security cases, integrity cases, load targets).

premium-ui-expert-v1 → storefront

  • Design brief in DESIGN.md: warm ivory palette with its own dark theme, one accent colour, system fonts, calm and confident motion.
  • Animation modules used: reveal on scroll, hero reveal, click-to-success on Pay, small hover and press effects. Skipped on purpose because there is no real data: sale pings, review shuffle, count-up stats.
  • Works under a strict security policy (no inline scripts or styles). Cart is a native dialog with focus handling. Rapid "Add to cart" clicks are queued so counts add up.
  • Every text and background colour pair is checked by a test in light and dark mode.

tester-expert-v1 → break-it tests, live checks, load test

  • Ran the race script (8 parallel payments, one order) and the IDOR script (other users and visitors get 404/401) against the live shop.
  • Wrote 16 break-it tests: double and repeated payments, Back/refresh, two buyers for the last item, tampered prices, bad quantities, forged cookies, injection-style ids, path tricks, odd Origin headers, rate limits, login lockout.
  • Checked the real browser: rapid double-click on Add to cart (3 clicks = 3 items) and on Pay (4 clicks = 1 paid order), no horizontal scroll on any page at phone width, dark mode renders.
  • Found the 4 bugs below, fixed each at its root, and added tests.

B-01 · A declined card emptied the cart
  • Steps: Add an item, pay with the "declined" test card, then try again.
  • Root cause: The failure path gave the stock back but not the cart, so the shopper had nothing left to retry with ("Your cart is empty").
  • Fix: Failure transaction now restores stock and cart together (capped at 20 per item).
  • Proof: break-it: "declined card…" and "after a decline, paying again…"
B-02 · "Origin: null" caused a server error (500)
  • Steps: Send a PUT with header Origin: null (browsers send this from sandboxed frames).
  • Root cause: new URL("null") throws inside the cross-site check, so the request crashed instead of being refused.
  • Fix: Bad or unparsable Origin is treated as foreign → 403.
  • Proof: break-it: "cross-site requests…" (4 origins)
B-03 · Expired session on the pay page: dead-end message
  • Steps: Log in, open checkout, let the session end, press Pay → "Something went wrong. Please try again." forever.
  • Root cause: The checkout handler had no case for 401.
  • Fix: 401 now sends the shopper to the login page with "Please log in to continue."
  • Proof: Reproduced and verified in the built-in browser (no automated browser test: Playwright is not installed)
B-04 · JS and CSS cached for an hour with no versioning
  • Steps: Change app.js, reload: the browser can keep running the old file.
  • Root cause: Static files had max-age=3600 and no file-name fingerprint.
  • Fix: Static files now revalidate. Production should use hashed file names plus long caching.
  • Proof: break-it: "static files are never served with a long cache lifetime" (added together with the fix, not red-first)

One failing check was not a bug: //server.mjs returns the shop's home page (200), not the source file. My test expected 404, so I corrected the test and kept the "no source code leaked" check.

Severity: S1 = money or data loss / security breach, S2 = core flow broken, S3 = works with a workaround, S4 = cosmetic. No S1 was found.

Known risks (not fixed, by design for a demo)

  • Account lockout lets someone lock a known email out for 15 minutes with wrong guesses.
  • A server crash between "stock reserved" and "payment attempted" leaves a pending order holding stock; needs a clean-up job.
  • Rate limits live in memory: they reset on restart and do not work across several server processes.
  • Only tested over plain HTTP; the Secure cookie and HSTS path was not exercised.

Breakpoint ramp: 10 → 2,500 req/s over up to 120 seconds

It broke. The test stopped by itself at about 551 requests/second because of errors above 5%. Latency stayed under 200 ms (p95) with no errors up to about 302 req/s. For comparison, the capacity estimate in BACKEND.md expects a real peak of about 3.5 req/s, so the shop has roughly 86× headroom on this machine.

The ramp was run twice. The first run did not record what kind of errors happened, so the numbers below are from a second, ramp-only run with error details added. The two runs broke at similar rates (about 530 and 550 req/s).

Where is the bottleneck?

  • What failed: 200 × 7152, 201 × 624, 409 × 116, ECONNREFUSED × 168. No server errors (no 5xx) and nothing in the server log. Every failure was ECONNREFUSED: the server could not accept new connections because its queue of waiting connections was full. That fits Node's default queue size of 511 (about 500 requests were in flight when it broke); this link was inferred from the numbers, not separately proven. 409 responses are expected: with only 40 test shoppers at this speed, two checkouts for the same person overlapped, and the second found an empty cart.
  • Highest server CPU seen: 87% of one core (the machine has 8 cores). The server is one Node.js thread, so it can use only about one core: that thread is the limit.
  • Load generator event-loop lag near the end: 20.7 ms (p99). Low: the generator was keeping up, so the measured limit is the server.
  • Requests the generator skipped because too many were already in flight: 0.
  • Memory of the server at the end: 105 MB.

  • Skills themselves: the three skills were exercised on one small project. A second, different project (for example Next.js with a real database) would show how well they generalise.
